# XM 自動シグナル判定

マルチタイムフレーム（1H / 4H / 8H / 日足）のテクニカル指標から15条件を自動判定し、
**BUY / SELL / WAIT** を出力するFXシグナルダッシュボードです。

> **実データで検証した結果、この判定ロジックに優位性は確認できていません。**
> ドル円 2012-11 〜 2022-03 の440トレードで勝率35.0%・PF 1.05、最大ドローダウン
> 1110 pips。同じ値動きでエントリーだけランダムにした対照実験（30.9〜37.3%）と
> 区別がつきません。詳しくは「[実データでの結果](#実データでの結果)」。
> このまま資金を入れないでください。
>
> **代わりに、このリポジトリの中身は「戦略の検証装置」です。**
> 1時間足7ルール・日足7ルールを12通貨ペアで試して全部落とし、1つだけ残った
> 「月初の逆張り」を1971年からの22通貨で確かめたら、**直近14年は本物・その前の
> 40年は逆向き**でした。優位性ではなく相場付きだった、というところまで見えます。
> 手順は「[入り方を変えて試す](#入り方を変えて試す7件全滅)」以降。

## データ元

既定では **Yahoo Finance のチャートAPI**（APIキー不要）から実データを取得します。

- 1H足: 直近60日 → EMA200の計算に十分な本数を確保
- 日足: 直近2年
- 4H / 8H足: Yahooが配信していないため1H足から集約して生成

**ネットワークが遮断されている環境やAPI障害時は、決定論的な合成データに自動フォールバック**します。
その場合はUI上部に警告バナーが出て、`dataSource: "synthetic"` がAPIレスポンスに入ります。
合成データのシグナルはデモ用で、実際の相場を反映していません。

常に合成データを使いたい場合:

```bash
MARKET_DATA_PROVIDER=mock npm run dev
```

対応シンボル: USDJPY / EURUSD / GBPUSD / EURJPY / GBPJPY / AUDUSD / XAUUSD

## API

```
GET /api/signal?symbol=USDJPY
```

`generateSignal` の結果一式（`signal` / `confidence` / `conditions` / `analysis` / `chartData`）に加えて、
`tradePlan`（エントリー・損切り・利確）、`dataSource`、`candleCounts` を返します。

## バックテスト

```bash
npm run backtest -- --symbol USDJPY
npm run backtest -- --symbol USDJPY --sweep buyRsiMax=60,65,70,75,80
npm run backtest -- --csv-1h data/usdjpy_1h.csv --csv-daily data/usdjpy_1d.csv
```

1H足を1本ずつ前進させながら `generateSignal` を呼び、BUY / SELL が出たらATRベースの
損切り・利確に到達するまで先の足でシミュレートします。トレード数・勝率・損益（pips）・
プロフィットファクター・期待値・最大ドローダウンをBUY / SELL別に出力します。

**先読み（lookahead）を避けるための約束事:**

- 判定に渡すのは評価中の足までのウィンドウのみ
- 日足はその時点で確定済みのものだけ渡す（形成中の日足の終値は使わない）
- エントリーはシグナルが出た足の終値ではなく**次の足の始値**で約定
- 同じ足の中で利確・損切りの両方に触れた場合は**損切りを優先**（悲観側に倒す）
- 同時に保有するポジションは1つまで
- **損切りと時間切れの決済は不利な方向に滑らせる**（`--slippage`、既定0.5pips）。
  損切りに達するのは値動きが速い局面なので、実際の約定は指定レートより悪くなる。
  利確は指値なので滑らせない

この決済ロジックは結果を大きく左右するので、`tests/backtest.test.ts` で
約定価格・pips換算・スプレッド控除・同一足で両側に触れた場合の扱いを固定しています。

### 主なオプション

| オプション | 既定値 | 内容 |

`--sweep` で振れるのは `buyScoreMin` / `sellScoreMin` / `buyRsiMax` / `sellRsiMin` の4つです。

挙動になります。

### CSVの形式

MT4 / MT5 のエクスポートをそのまま読めます。判別は自動です。

- 区切り文字: カンマ / タブ / セミコロン
- ヘッダ: `<DATE>` のような山括弧付き、`timestamp` `datetime` などの別名、ヘッダ無しも可
- 日付と時刻: 別列（MT5の `<DATE>` + `<TIME>`）でも1列にまとまっていても可
- 日付区切り: `2024.01.15` `2024/01/15` `2024-01-15`、エポック秒/ミリ秒も可

MT5からの出し方: チャートを開いて `F2`（気配値 → 銘柄 → バー）でエクスポート、
または「ファイル」→「データフォルダを開く」から `history` を書き出します。
1H足と日足の両方が必要です。

**タイムゾーンに注意。** 時刻にタイムゾーン表記が無い場合はUTCとして扱います。
MT5のサーバー時刻は多くがEET（UTC+2、夏時間はUTC+3）なので、そのまま渡すと
セッション判定（ロンドン / ニューヨーク）が2〜3時間ずれます。ずれたまま流すと
セッションフィルターの効き方が変わるので、事前にUTCへ直してください。

読み込み時に、同じ時刻の重複・時間の飛び・高値安値の矛盾を点検して報告します。

必要な本数は1H足が1000本以上（EMA200のウォームアップ）、日足が210本以上です。

### 実データについて

`--csv-*` を指定しない場合はYahoo Financeから取得します。ネットワークが使えない環境では
合成データにフォールバックしますが、**合成データはランダムウォークなので再現可能な
優位性が存在せず、出てくる数値は基盤の動作確認にしかなりません。**
戦略の評価には必ず実データを使ってください（実行時にも警告が出ます）。

実データは次のコマンドで取れます。

```bash
npx tsx scripts/fetchRealData.ts --out data
npm run backtest -- --csv-1h data/usdjpy_h1_utc.csv --csv-daily data/usdjpy_d1_utc.csv
```

取得元は [ejtraderLabs/historical-data](https://github.com/ejtraderLabs/historical-data)
（GitHubの公開リポジトリ）です。このデータは2つの点でそのままでは使えないので、
スクリプトが直します。**どちらも黙って結果を狂わせる種類のずれです。**

- 価格が1000倍の整数（`81121` = 81.121）。そのまま読むとATRもpipsも桁が狂う
- 時刻がブローカーのサーバー時刻（EET/EEST）。UTCに直さないとセッション判定が2〜3時間ずれる

EETであることはデータの中身から確かめられます。金曜の最終足が23時・月曜の初足が0時で、
これが夏冬どちらでも変わりません（UTC固定やUTC+1固定なら季節でずれます）。さらに
金曜22時終わりが3月と11月に集中していて、EUとUSの夏時間切替日のずれと一致します。

### 実データでの結果

**ドル円 2012-11 〜 2022-03（1H足57,600本 / 9年4か月）、440トレード。**

| | |
| --- | --- |
| 勝率 | **35.0%**（154勝 286敗） |
| 損益 | +303.2 pips |
| プロフィットファクター | **1.05** |
| 期待値 | 0.69 pips/トレード |
| 最大ドローダウン | **1110.8 pips** |
| 最大連敗 | 18 |

**この戦略には、実データ上の優位性が確認できません。** 理由は3つあります。

**1. ランダムエントリーと区別がつきません。** 同じ値動き・同じコスト・同じ件数で、
エントリーだけをランダムにした対照実験の勝率は 30.9% / 33.4% / 33.9% / 34.8% / 37.3%。
戦略の35.0%はこの散らばりの中にあり、5本中1本のランダムは損益でも戦略を上回りました。

**2. 損益は変換の誤差以下です。** 1H足を丸ごと±3時間ずらして走らせると、
損益は -193.7 〜 +515.2 pips の間を動きます（勝率は35〜36%で動きません）。
+303 pipsは、時差の取り方を1時間変えれば消える大きさです。

**3. 後半で崩れています。** 440件を4等分すると、前半2つが +237 / +1024 pips、
後半2つが -551 / -407 pips。9年で+303 pipsのうち、稼いだのは前半だけです。

#### 勝率60%は達成できます。そして達成すると損をします

同じシグナルのまま、利確の位置だけを変えた結果です。

| リスクリワード | 損益分岐勝率 | 実際の勝率 | 損益 | PF |
| --- | --- | --- | --- | --- |
| 1:0.5 | 66.7% | **62.9%** | **-866.4 pips** | 0.82 |
| 1:0.75 | 57.1% | 55.6% | -230.5 pips | 0.96 |
| 1:1 | 50.0% | 50.6% | +155.6 pips | 1.03 |
| 1:1.5 | 40.0% | 41.6% | +161.9 pips | 1.03 |
| 1:2 | 33.3% | 35.0% | +303.2 pips | 1.05 |
| 1:3 | 25.0% | 26.7% | +42.2 pips | 1.01 |

利確を近づければ勝率は上がります。1:0.5にすれば62.9%で、目標の60%を超えます。
そして866 pipsの負けになります。**勝率は利確の置き方で決まる数字であって、
判定ロジックの性能ではありません。**

そしてこの表の本当の読みどころは、**実際の勝率がどの比率でも損益分岐勝率の
1〜2ポイント上にしか出ていない**ことです。これは「エントリーに予測力が無い」
ときに出る形そのものです。予測力があるなら、比率を変えても損益分岐を明確に
上回り続けるはずです。

### 入り方を変えて試す（7件、全滅）

閾値をいじっても仕方がないので、**入り方の発想そのもの**を差し替えて同じ土俵で
比べました。

```bash
npx tsx scripts/hypothesis.ts --csv-1h data/usdjpy_h1_utc.csv
npx tsx scripts/hypothesis.ts --csv-1h data/usdjpy_h1_utc.csv --rule tokyo_fix_fade
```

決済とコストは既存のバックテストと同じ経路を通すので、差が出るのは入り方だけです。

**手順は3つ。どれか1つでも省くと、偶然を実力と読み違えます。**

1. **期間を分ける。** 前半60%（2012-11〜2018-06）で見て、後半40%は選定に使わない
2. **対照を2種類置く。**
   - *時刻ランダム*: 同じ本数だけ、でたらめな時刻に入る → 「入る時刻を選べているか」
   - *向きランダム*: **同じ時刻で**向きだけコインで決める → 「向きを当てられているか」
3. **試した数を数える。** 7つ試せば、対照を上回るものが1つ出るのは普通のこと

結果（勝率、学習期間 → 検証期間）:

| ルール | ねらい | 学習 | 検証 | 判定 |
| --- | --- | --- | --- | --- |
| ボリンジャー逆張り | 行き過ぎは戻る | 32.9% | 33.0% | 対照と区別なし |
| RSI反転 | 極値からの折り返し | 31.6% | 33.1% | 対照を**下回る** |
| 素の順張り | 条件を足さない追随 | 34.7% | 34.3% | 検証で区別なし |
| ロンドン開始のブレイク | 時間帯の性質 | 34.4% | 36.6% | 検証で区別なし |
| 東京仲値の戻り | 実需で動いた分は戻る | 35.2% | 36.0% | **学習で**区別なし |
| 上位足に沿った押し目 | 大きな流れに乗る | 33.2% | 34.7% | 対照と区別なし |
| ロンドン時間の継続 | その日の方向に乗る | 33.8% | 34.4% | 対照と区別なし |

**7件すべて落ちました。** 損益も、東京仲値の戻りの検証期間（+53.8 pips / 414件 =
0.13 pips/件）以外はすべてマイナスです。

そして一番痛い比較がこれです。**既存の15条件（35.0%）は、EMA20と24本前の終値を
見るだけの「素の順張り」（34.7% / 34.3%）を上回っていません。** 15の条件は
トレード数を減らしているだけで、勝率を足していませんでした。

#### 対照実験のほうにバグがありました

最初に組んだ「時刻ランダム」は、候補足からくじを引いて既存の保有と重なったら
引き直す方式でした。件数が多いとこれが効いて、**長く持つトレードほど棄却されます。**
損切りは利確より近いので、長く持つのは勝ちに向かっている側になりやすく、
結果として対照の勝率が不当に低く出ます。2380件を引かせたら勝率23.4%まで落ちました
（1:2なら33%前後になるはず）。**対照が弱くなると、ルールが良く見えます。**

棄却をやめて、戦略と同じように前へ進みながら確率で入る形に直したところ、
どの期間でも32〜35%に収まりました。上の表はその修正後の数字です。

### 日足に移して、12通貨ペアで試す（7件、全滅）

1時間足をやめた理由はコストの比率です。1時間足のATRは10 pips前後で、そこに
1.5 pipsのスプレッドと滑りが乗ります。日足のATRは45〜160 pipsなので、
**同じコストが10分の1以下の重さ**になります。あわせて、日足なら同じ手間で
12通貨ペアぶんの証拠が集まります。

```bash
npx tsx scripts/fetchRealData.ts --symbols all --timeframe d1 --out data
npx tsx scripts/hypothesis.ts --timeframe daily --dir data
```

12ペア（USDJPY EURUSD GBPUSD EURJPY GBPJPY AUDUSD AUDJPY EURCHF EURGBP
USDCAD USDCHF XAUUSD）× 各2400本、2012-12〜2022-03。2018-06で学習と検証に分けます。

| ルール | 学習（勝率 / 損益 / プラスの銘柄） | 検証 | 判定 |
| --- | --- | --- | --- |
| 20日ブレイクアウト | 35.6% / +1446 / 8-12 | 31.7% / **-4055** / 2-12 | 学習だけ |
| 55日ブレイクアウト | 35.1% / -677 / 4-12 | 32.7% / +2048 / 3-12 | 学習だけ |
| 50日/200日クロス | 30.7% / -1559 / 5-12 | 32.9% / -1847 / 7-12 | 区別なし |
| 時系列モメンタム | 33.5% / +3274 / 6-12 | 35.6% / -203 / 4-12 | 区別なし |
| 長期の方向への短期逆張り | 31.0% / -4496 / 4-12 | 35.5% / -1164 / 7-12 | 区別なし |
| インサイドバーのブレイク | 32.4% / -4367 / 3-12 | 39.0% / **+11825** / 8-12 | **検証だけ** |
| 月初 | 30.6% / -9899 / 4-12 | 34.8% / +3509 / 6-12 | 区別なし |

**7件すべて落ちました。** 20日/55日ブレイクは学習期間だけ対照を上回り、
インサイドバーは検証期間だけ上回りました。**順序が逆です。**
7ルール×2期間で3つ当たりが散らばるのは、偶然そのものの形です。

#### 検証期間で良く見えたものは、いつ稼いだのか

四半期別に見ると答えが出ます。

| ルール | 検証期間の損益 | 最大の四半期 | 割合 |
| --- | --- | --- | --- |
| 55日ブレイクアウト | +2048 pips | 2020Q1（+2281） | **111%** |
| 月初 | +3509 pips | 2021Q1（+3734） | **106%** |
| インサイドバーのブレイク | +11825 pips | 2020Q2（+3338） | 28%（2020上期で51%） |

前の2つは**一度の四半期を除くと負けます。**「効いた」のではなく「居合わせた」だけです。

インサイドバーだけは事情が違って、2020年を除いても16四半期中9つが黒字です。
ただし同じルールが**学習期間（2012-2018）では -4367 pips・12ペア中3ペアしか
黒字でない**のも事実です。同じ12ペアで前半は明確に悪く後半は明確に良い、というのは
優位性の形ではなく、相場付き（この場合はボラティリティ）に依存する形です。
候補にはしません。

#### 日足でも構造は変わりませんでした

コストの比率は10分の1以下になり、証拠は12倍になりました。それでも
**勝率はどのルールも30〜39%で、1:2の損益分岐（33.3%）の周りに張り付いたまま**です。
1時間足で見えた「実際の勝率が損益分岐の1〜2ポイント上にしか出ない」形は、
日足でもそのままでした。コストが原因ではなかった、ということです。

### 決済を外して、シグナルそのものを測る

ここまでの検証はすべて同じ決済（1.5ATRの損切り・1:2の利確）を通していました。
そしてどのルールも勝率が損益分岐のすぐ上に張り付きました。これは2通りに読めます。

- (a) エントリーに情報が無い
- (b) 情報はあるが、この決済が捨てている

**損切りは経路に依存します。**行き先が同じでも途中で損切りに触れば負けです。
だから決済を挟んだ計測は、この2つを区別できません。**区別していませんでした。**

```bash
npx tsx scripts/predictive.ts --timeframe daily --dir data
```

決済もコストも外し、シグナルの n日後の終値だけを見ます。有意性は並べ替え検定で
測ります（期間の重なるシグナルは独立ではないので、t検定は使えません）。

日足7ルール × 5期間 = 35通り。**p < 0.05 は2件、偶然の期待値は1.8件。**
つまり (a) でした。決済の工夫では解決しません。

### ただし、2件とも同じルールで、符号がマイナスでした

`月初`（前月と同じ方向に入る）が**逆に効いていました。**符号を反転させて追いかけます。

**⚠ これは事後に見つけたものです。**先に立てた仮説ではなく、失敗したルールの
符号をひっくり返しただけ。そして反転させた時点で、見つけるのに使った
12ペア・2012〜2022年はもう検証に使えません。

5日間の時間決済で回すと、学習 53.0% / +5406 pips / 8-12ペア、
検証 54.1% / +5948 pips / 9-12ペア。**両期間で同じ符号・同じ規模。**
ここまで一貫したものは他にありませんでした。

米連邦準備制度のH.10（対ドル日次レート、**1971年〜2026年**）を使います。

**発見後は確かに出ました。**2022〜2026年は一度も見ていないデータで、
p < 0.0001、8通貨中7通貨。これは本物の標本外確認です。

**そして発見前の40年は、逆向きに同じくらい強く出ています。**8通貨中7通貨が
マイナス。しかも符号は単調に動いています。

| 期間 | 平均 | プラスの通貨 |
| --- | --- | --- |
| 1971〜1984 | -0.1654 | 1/8 |

偶然の反転ではありません。**55年かけて順張りから逆張りへ、少しずつ入れ替わっています。**

#### だから、これは優位性ではなく相場付きです

言えることは3つです。

1. **直近14年、月初の逆張りは効いています。**別の出所・別の通貨・見ていない
   期間で確認できました
2. **その前の40年は、同じことをやると同じくらい負けました**
3. **どちらの相場付きにいるかは、後になるまで分かりません**

1990年にこれを見つけた人は、順張り版を「40年で確認済み」として売れたはずです。
そして2012年以降に破産します。**いま逆張り版を「14年で確認済み」として使うのは、
同じことをしています。**

もし使うなら、恒久的な優位性ではなく**相場付きへの賭け**として扱ってください。
枚数を抑え、符号が戻り始めていないかを毎月見ること。

#### この結果は合成データの結論をひっくり返します

モンテカルロでは戦略が20系列中17系列でランダムを上回っていました。それは
合成系列に持続的なトレンドがあり、トレンド追随の判定がそれを拾えたためです。
**実際のドル円にはその性質がありませんでした。** 合成データで測った優位性は、
発生器の性質を測っていたのであって、戦略を測ってはいませんでした。

このリポジトリの合成データ由来の数字（シグナル頻度を含む）は、すべて
「実装が動いていること」の確認であって、成績の根拠ではないものとして読んでください。

## パラメータ探索

```bash
npm run optimize -- --min-win-rate 60
npm run optimize -- --csv-1h data/usdjpy_1h.csv --csv-daily data/usdjpy_1d.csv --min-win-rate 60
```

判定の閾値と決済条件を総当たりで試し、成績を比べます。

### 勝率を目標にしてはいけない理由

**勝率は利確幅を狭めるだけで機械的に上がります。** 同じデータ・同じ判定ロジックで
リスクリワードだけを振ると、こうなります。

| リスクリワード | 勝率 | 損益 | PF | 期待値 |
| --- | --- | --- | --- | --- |
| 1:0.5 | 66.2% | −92.6 pips | 0.88 | −1.25 pips |
| 1:1 | 46.4% | −236.0 pips | 0.80 | −3.42 pips |
| 1:2 | 38.1% | +202.3 pips | 1.17 | +3.21 pips |
| 1:3 | 35.6% | +688.6 pips | 1.58 | +11.67 pips |

**一番勝率が高い設定が一番損をして、一番勝率が低い設定が一番儲かっています。**
利確を近づければ当たる回数は増えますが、1回あたりの利益が減り、
損切り幅は変わらないので割に合わなくなります。これはデータの性質ではなく
損益計算上の関係なので、実データでも同じことが起きます。

そのため `optimize` は**勝率を制約条件**として扱い、順位づけは
**期待値（1トレードあたりの平均pips）**で行います。`--min-win-rate` を指定すると
その勝率を満たす設定だけに絞り込みますが、制約なしの結果も併記するので、
勝率にこだわった場合にいくら失っているかが見えます。

### カーブフィットの検出

期間を前半と後半に分け、**前半だけで探索して後半の成績を併記**します。
前半で良くて後半で崩れる設定は、たまたま前半の値動きに合っていただけです。
両方の列を見て、差が小さいものを選んでください。

`--split 0.6` で分割位置を変えられます（既定は前半60%）。

## 戦略パラメータの設定

探索で見つけた設定は、環境変数でアプリと通知の両方に反映できます。

| 環境変数 | 既定値 | 内容 |
| --- | --- | --- |
| `SIGNAL_BUY_SCORE_MIN` | `0.65` | BUYを通す重み付きスコアの下限（0〜1） |
| `SIGNAL_SELL_SCORE_MIN` | `0.65` | SELL A型スコアの下限（0〜1） |
| `SIGNAL_BUY_RSI_MAX` | `70` | これ以上のRSIではBUYを出さない |
| `SIGNAL_SELL_RSI_MIN` | `30` | これ以下のRSIではSELLを出さない |
| `TRADE_ATR_STOP` | `1.5` | 損切り幅 = ATR × この倍率 |
| `TRADE_RISK_REWARD` | `2` | 利確幅 = 損切り幅 × この倍率 |
| `ACCOUNT_BALANCE` | `0` | 口座残高。設定するとロット数を計算して表示します |
| `RISK_PERCENT` | `2` | 1トレードで許容する損失の割合（%） |

```bash
TRADE_ATR_STOP=2 TRADE_RISK_REWARD=1.5 npm run dev
ACCOUNT_BALANCE=1000000 RISK_PERCENT=2 npm run dev   # ロットも表示する
```

`ACCOUNT_BALANCE` を設定すると、損切り幅から逆算したロット数と、損切りに達した
場合の損失額が売買プランに出ます。損切りが広い局面では自動的にロットが小さくなり、
1トレードで失う金額が一定に保たれます。

**口座通貨と決済通貨が異なる場合は換算レートが必要です。** 円口座でEUR/USDを
扱う場合など、レートが渡されなければロットを計算せず理由を表示します
（推測すると実際のリスクがずれるため）。

範囲外や数値でない値は**無視して警告を出します**。黙って既定値に落ちると、
設定したつもりで効いていない状態に気づけないためです。

## シグナル通知

シグナルが出たときに Discord / Slack へ通知します。

```bash
export SIGNAL_WEBHOOK_URL="https://discord.com/api/webhooks/..."

npm run watch                                    # 5分ごとに判定（常駐）
npm run watch -- --once                          # 1回だけ判定（cron / GitHub Actions 用）
npm run watch -- --symbols USDJPY,GBPJPY --interval 300
npm run watch -- --once --allow-synthetic        # Webhookの疎通確認
```

Webhookのペイロードには `content`（Discordが読む）と `text`（Slackが読む）の両方を
入れているので、URLを差し替えるだけでどちらでも動きます。`SIGNAL_WEBHOOK_URL` が
未設定なら標準出力に出力します。LINEやメールに送りたい場合は `lib/notifier.ts` の
`Notifier` インターフェースを実装して差し替えてください。

### どれくらいの頻度で出るか

**ほとんどの時間はWAITです。** 合成系列8本・22,416時間ぶんを1時間足1本ごとに
判定して数えた結果:

| | |
| --- | --- |
| WAIT以外だった割合 | 1.40%（BUY 123 / SELL 190） |
| シグナルが出る間隔 | 1銘柄あたり平均 103時間（約4.3日）に1回 |
| 出ている時間 | 1回あたり平均 1.4時間 |

つまり **画面を開きに来る使い方では、まず取り逃します**。1日1回ダッシュボードを
見る運用だと、平均1.4時間しか出ていないものを24時間に1回覗くことになります。
通知（`npm run watch`）を前提にしてください。

逆に言えば、ダッシュボードが何日もWAITのままでも、それは取得が止まっている
わけでも壊れているわけでもありません。データの鮮度は画面上部の更新時刻で
確認できます。

（この数字は合成データでの計測です。実際のドル円での頻度は
「[実データについて](#実データについて)」のとおり、まだ確かめられていません。）

### 通知が鳴る条件

**前回の判定から状態が変わったときだけ**送ります。BUYが続いている間ずっと鳴ると
通知の意味が無くなるためです。

| 前回 | 今回 | 通知 |
| --- | --- | --- |
| WAIT | BUY / SELL | エントリー通知（価格・損切り・利確・信頼度つき） |
| BUY | SELL | エントリー通知（反転） |
| BUY / SELL | WAIT | 解除通知 |
| 同じ状態の継続 | | 通知しない |

状態は `--state` のファイル（既定 `.signal-state.json`）に保存します。cronで回す場合も
このファイルが引き継がれる場所を指定してください。**送信に失敗したときは状態を進めない**
ので、次回の実行で再送を試みます。

**実データを取得できないときは通知しません。** 合成データのシグナルを通知すると
実際の相場と誤認する危険があるためです。Webhookの設定を確認したいだけの場合は
`--allow-synthetic` を使ってください（通知本文に「テスト」が入ります）。

### 実行場所

`--once` があるので、常駐でもcronでも同じスクリプトが使えます。

```bash
# 常駐（VPS・自宅PC）
npm run watch -- --interval 300

# cron: 平日のロンドン・NY時間（JST 16時〜翌2時 = UTC 7時〜17時）に5分ごと
*/5 7-17 * * 1-5 cd /path/to/XM && npm run watch -- --once --state /var/lib/xm/state.json
```

判定はロンドン（JST 16-21時）とNY（JST 21-翌2時）以外では必ずWAITになるので、
それ以外の時間帯に回しても通知は出ません。

## フォワードテスト

バックテストが良くても、実運用が同じ成績になるとは限りません。実際に出した
シグナルを記録して、後から値動きと突き合わせます。

`npm run watch` はシグナルを出すたびに記録を追記します（既定 `.signal-log.jsonl`、
`--log` で変更可）。1行1件のJSONLなので、途中でプロセスが落ちてもそれまでの行は
残ります。

```bash
npm run reconcile                                   # 記録を値動きと突き合わせる
npm run reconcile -- --log /var/lib/xm/signals.jsonl
npm run reconcile -- --csv-1h data/usdjpy_1h.csv --symbol USDJPY
```

記録した各シグナルについて、その後の足で損切り・利確のどちらに到達したかを判定し、
勝率と損益を出します。判定の約束事はバックテストと揃えてあります（同じ足で
両側に触れたら損切り扱い）。**記録に使った足そのものは判定に使いません**
（それは判定済みの足なので、含めると先読みになります）。

### 読むときの注意

- **スプレッドを差し引いていません。** バックテストの数字と比べる際は、
  その分だけこちらが有利に出ています
- **決着30件未満では勝率の振れ幅が大きすぎます。** 実力の判断には足りません
- 「照合不能」が多い場合は、記録より後の足が取得できていない可能性があります
  （既定のYahoo取得は直近60日ぶん）

バックテストと大きく食い違うなら、その差の原因を調べる価値があります。
考えられるのは、スプレッドや滑り、約定タイミングの差、データの違いなどです。

## 資金管理

`lib/positionSizing.ts` が、損切り幅とリスク許容度からロット数を出します。

```
ロット = 残高 × リスク割合 ÷ (損切りpips × 1ロットあたりのpip価値)
```

**pipsは金額ではありません。** 「最大ドローダウン200pips」が痛いかどうかは、
1pipあたりいくら賭けているかで決まります。損切り幅が広い局面では自動的に
ロットが小さくなり、1トレードで失う金額が一定に保たれます。

- 刻みへの丸めは**必ず切り捨て**ます（切り上げると意図したリスクを超えるため）
- 最小ロットに満たない場合は0を返し、理由を添えます
- 換算レートは推測せず**必須入力**です。ここで適当な値を仮定すると、
  ロットが静かにずれて実際のリスクが変わります

## 勝つために必要な数字

```bash
npm run edge
npm run edge -- --spread 1.8 --atr 10 --rr 2 --risk 2
npm run edge -- --atr 90 --win-rate 54.1 --avg-win 102 --avg-loss 96 --risk 1
```

検証の結論は「価格から方向は当てられなかった」でした。当てられないなら、
**当てにいかないところで勝負を決める**しかありません。ここは予測を1つも
含まない3つの計算で、どれも相場が何をするかに関係なく成り立ちます。

### 1. その設定で損益が±0になる的中率

```
p = (損切り幅 + コスト) / (利確幅 + 損切り幅)
```

XMスタンダードのドル円（往復2.3 pips）で、1時間足のATR 10 pips・RR 1:2 なら:

| | |
| --- | --- |
| コストが無ければ | 33.3% |
| 実際のコストでは | **38.4%** |
| コストは損切り幅の | 15.3% |

**+5.1ポイント。**そしてこのリポジトリの判定ロジックの実測は35.0%でした。
つまり1時間足では、始める前から成立していません。**日足（ATR 90 pips）なら
同じコストで +0.6ポイント**にしかなりません。上位足に移す理由は勘ではなく
この比率です。

この数字はダッシュボードにも常時出ます（WAITのときも）。エントリーの根拠より
先に必要なのは「何%当てれば±0か」だからです。

### 2.「運ではない」と言うのに要るトレード数

```
n ≧ ( 1.96 × ばらつき / 期待値 )²
```

**期待値がばらつきに対して小さいほど、必要件数は二乗で増えます。**

月初の逆張り（実測54.1%、平均利益102 / 平均損失96 pips）で計算すると:

| | |
| --- | --- |
| 1トレードの期待値 | 8.82 pips |
| 1トレードのばらつき | 98.7 pips |
| 必要件数（95%） | **339件** |

月初は1銘柄あたり年12件。12通貨ペアを同時に回して年144件なので、
**約2.4年**やって初めて「運ではない」と言えます。
「3か月やって勝てたから本物」は、この計算では何も言えていません。

### 3. その枚数で口座がどこまで減りうるか

期待値がプラスでも枚数で壊れます。的中率40%・RR 1:2（期待値はプラス）で
1回20%賭ければ破産します。残高比で賭け続ける形を5000回まわして数えます。

損益分岐ちょうどの的中率・1回2%・200トレードだと、**残高が半分になる確率が6.4%**。
1%に抑えるなら1回1%までです。

**注意: 的中率は決済条件とセットでしか意味を持ちません。** 時間で切る決済で
測った54%を1:2の損切り利確に当てはめると、勝ち幅が実際の倍近くになって
期待値が跳ね上がります。`--avg-win` / `--avg-loss` に実測の平均幅を渡すと、
そこを分けて計算します（渡さない場合は警告が出ます）。

だけを読み上げる `role="status"` の領域を追加しています（画面全体を live region に
すると更新のたびに全項目を読み上げてしまいます）。

**薄さに意味を持たせないこと。** 「評価対象外」を薄い文字で表していたのは、
情報を色の濃さだけで伝えていたということです。除外であることは「?」の印と
「評価対象外」の札で読み取れるので、読みにくさを情報の代わりにする必要は
ありませんでした。

## 判定ロジックの概要

条件は4カテゴリ・計15項目で、それぞれ重み1〜5を持ちます。

- **トレンド確認** — 1Hトレンド、MTF整合性（重み5）、ダウ理論構造
- **エントリー条件** — 20EMA方向、押し目/戻り目（重み4）、サポレジ（重み4）
- **確認シグナル** — RSI、ダイバージェンス、反転ローソク足（重み4）、ボリンジャーバンド、MACD
- **フィルター** — ボラティリティ、時間帯、経済指標、スプレッド

シグナル確定までに、さらに次のフィルターを通します。

1. コア条件（1Hトレンド + MTF整合性）と経済指標フィルターが必須
2. MTFフィルター — 4H MACDの向きと8Hトレンドが方向と一致すること
3. セッションフィルター — ロンドン（JST 16-21時）またはNY（JST 21-翌2時）のみ
4. BUYは重み付きスコア65%以上、SELLは独立スコアリング（`calculateSellScoreA`）で65%以上
5. 過熱 / 過売りフィルター（ボリンジャーバンド、MACDクロス、RSI）

## 既知の制約

- **経済指標フィルターは、実際の発表予定を渡さなければ推定になります。**
  `generateSignal` の `economicEvents` に予定を渡せばそれを使います。渡さない場合は
  主要指標の定例時刻（JST 21:30 / 22:00 / 03:00 / 12:00）の前後30分を危険時間帯として
  推定し、条件の表示に「（推定）」と残します。実際のスケジュールとはズレます。
- **スプレッド条件は、実スプレッドを渡さなければ判定から除外されます。**
  ローソク足からは実スプレッドを知る術がないため、`spreadPips` を渡さない限り
  この条件はスコアの分子からも分母からも外れます（以前は常に成立扱いになっており、
  スコアを底上げしていました）。実運用ではブローカーのbid/askから求めた値を
  渡してください。
- **4H / 8H足は1H足から合成しています。** 区切りはUTCの絶対時刻に揃えてあるので取得
  タイミングでブレませんが、週末をまたぐバケットは本数が欠けるため、ブローカー配信の
  4H / 8H足とは完全には一致しません。
  なお `generateSignal` は8H足を省略すると内部で1H足を先頭から8本ずつ数えて集約します。
  この方式は取得ウィンドウがずれると区切りもずれるため、本アプリでは常に
  `lib/marketData.ts` の `aggregate` で作った8H足を明示的に渡しています。
- 表示している `confidence` は条件の重み付き充足率がベースなので、
  WAIT のときも数値が高く出ることがあります（「エントリーすべき確度」ではありません）。
- **シグナルの発火頻度は低めです。** 多段フィルターを通すため、1H足9000本
  （約1年分）のバックテストで成立するトレードは50件程度でした。
  BUY / SELL が発火しなくなる変更に気づけるよう、`tests/signalReachability.test.ts` で
  実際に発火する相場をシード固定して回帰テストにしています。

  なお `RSI >= 70 → WAIT` フィルターの効き方は、検証に使う値動きの性質に強く依存します。
  ドリフトが一定のランダムウォークではRSIが高止まりするためBUY候補の大半を落としますが、
  一定間隔でトレンドが転換するより現実的な値動きでバックテストすると、
  このフィルターを外して（`buyRsiMax=100`）もトレードは47件から50件（BUYは21件から24件）に
  増えるだけでした。閾値を調整する際は必ず実データで確認してください。

## 判定式の修正履歴

ランダムウォークで条件ごとの成立率を計測したところ、2つの条件の判定式が後段のOR節に
吸収されて意図が消えていたため修正しました。

**ダイバージェンス条件** は `divergence !== "none"` に潰れており、上昇トレンド中の
ベアリッシュ・ダイバージェンスでも成立していました。計測では成立532件のうち529件
（99.4%）がトレンドと逆向きで、シグナルに不利な材料が重み2の加点になっていました。

ただし単純に順張り一致（上昇トレンド＋ブリッシュ）だけを成立条件にすると、今度は
条件が死にます。ダイバージェンスは本質的に反転指標で、トレンドと同じ向きのものは
相場付きによらず0.2〜0.7%しか出現しないためです（定常トレンド / 120本ごとの転換 /
40本ごとの転換の3パターンで計測）。そこで **「トレンドに逆行するダイバージェンスが
出ていないこと」を成立条件** としました。成立率は56.7%で、逆行ケースは正しく不成立に
なります。

**ダウ理論構造の条件** も `marketStructure !== "RANGE"` に潰れていたため、
トレンドと構造が一致する場合のみ成立するようにしました（成立率 82.8% → 77.9%）。
こちらは順張り一致が十分な頻度で出るため、そのまま厳格化しています。

この2つは判定式にOR節を足すと再び潰れやすいので、`tests/autoSignalEngine.test.ts` に
「逆行している材料が成立扱いになっていないこと」を多数の相場で確認する性質テストを
入れてあります。逆行ケースを実際に観測できていることも同時に検証しているので、
テストが空振りすることはありません。

### スコアの下駄

フィルター4条件（ボラティリティ / 時間帯 / 経済指標 / スプレッド）は計測上ほぼ常に
成立するため、重み41点中7点が実質固定で乗っています。特にスプレッド判定は実配信が
ないため常に成立します。BUYの閾値65%を調整する際はこの下駄を考慮してください。
